# Soup — очередь задач обучения моделей (V2)

## Запуск

Необходимы Docker Engine/Desktop и Docker Compose версии 2.24.4 или новее:
тестовый стенд использует `!override`. Для тестов нужен Python 3.10+.
Локальная установка Go 1.27.4+ необязательна: Docker собирает приложение сам.

```bash
docker compose up
```

Команда собирает образ, запускает PostgreSQL, RabbitMQ и publisher, применяет миграции и запускает API
на `127.0.0.1:8080` и **четыре независимых контейнера воркеров**. Для первоначальной
загрузки образов нужен доступ к сети. Порт БД не публикуется на хосте. Данные
сохраняются в именованном томе между перезапусками. Проверка готовности доступна
по `/health`; её также выполняет Compose.

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f api worker
docker compose up -d --scale worker=8
docker compose down                 # сохраняет том с данными БД
# docker compose down --volumes     # удаляет данные ЭТОГО Compose-проекта
```

По умолчанию при локальном запуске аутентификация API отключена, а порт привязан
только к loopback-интерфейсу. Другие контейнеры в сети этого Compose-проекта могут
обращаться к API. Чтобы включить проверку bearer-токена, задайте `API_TOKEN`
в `.env`. Значения по умолчанию перечислены в `.env.example`. Если порт 8080 занят,
измените `API_PORT`. Не предоставляйте удалённый доступ к API без аутентификации.
При запуске нескольких экземпляров используйте отдельное имя проекта
`-p soup-yourname` и указывайте его во всех командах для этого экземпляра.

## Контракт API

Для JSON-запросов нужен `Content-Type: application/json`. Обработчики приложения
возвращают JSON. Для неизвестных маршрутов и неподдерживаемых методов стандартный
HTTP-маршрутизатор возвращает текстовые ответы 404/405.

Если `API_TOKEN` задан, все маршруты, кроме `/health`, требуют заголовок
`Authorization: Bearer <token>`; иначе возвращается 401. Общий токен предоставляет
доступ ко всем заданиям. Разграничения владения заданиями между пользователями нет.

```bash
curl -i http://127.0.0.1:8080/jobs \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: example-001' \
  -d '{"model":"resnet-demo","duration_ms":1000,"max_attempts":5}'
curl http://127.0.0.1:8080/jobs/1
curl 'http://127.0.0.1:8080/jobs?limit=20&after=0'
curl -X POST http://127.0.0.1:8080/jobs/1/cancel
curl http://127.0.0.1:8080/health
# При включённой аутентификации добавьте: -H "Authorization: Bearer $API_TOKEN"
```

| Маршрут | Поведение и HTTP-коды |
|---|---|
| `POST /jobs` | `Idempotency-Key`: 1–128 печатных ASCII-байтов без пробелов. 201 — новое задание; 200 — повтор с теми же нормализованными данными; 409 — существующий ключ с другими данными. |
| `GET /jobs/{id}` | 200 — текущее состояние задания. ID — положительное число int64; 400 — некорректный ID, 404 — задание не найдено. |
| `GET /jobs?limit=50&after=0` | `limit` от 1 до 100; курсор `after` — неотрицательное число int64. Ответ: `{jobs: [...], next_after: n}`. Продолжайте обход до пустой страницы. |
| `POST /jobs/{id}/cancel` | 200 — переход queued/running → cancelled или повторная отмена; 409 — задание уже succeeded/failed; 404 — не найдено. |
| `GET /health` | 200 — БД доступна, иначе 503. Не требует аутентификации и не раскрывает конфигурацию. |

Поля запроса создания:

- `model` — обязательная строка длиной 1–128 байтов после удаления пробелов по краям.
- `duration_ms` — целое число от 0 до 60000, по умолчанию 0.
- `max_attempts` — от 1 до 20; отсутствие поля или 0 означает 5 попыток.
- `fail_until_attempt` — от 0 до 20, по умолчанию 0. Явно включает имитацию ошибки:
  первые N попыток завершаются без эффекта. Повторы продолжаются до исчерпания
  разрешённого числа попыток.

Неизвестные поля, дополнительное JSON-значение после тела запроса, неверные типы
и значения вне диапазона возвращают 400. Неподдерживаемый тип содержимого — 415,
тело больше 4096 байтов — 413. Повторяющиеся имена JSON-полей обрабатываются
по правилам декодера Go: используется последнее значение; клиентам не следует
отправлять такие запросы. JSON `null` в скалярных полях соответствует их нулевому
значению.

Ответ с заданием содержит `id`, `payload`, `status`, `attempts`, `max_attempts`,
`lease_until` во время выполнения, временные метки БД и необязательное поле
`last_error`. Fencing token используется внутри системы и не возвращается клиенту.

Переходы состояний: queued → running → succeeded/failed. Имитируемая ошибка может
вернуть задание в очередь; running-задание с истёкшей арендой может быть получено
повторно. Из queued/running возможен переход в cancelled.

Отмена и завершение упорядочиваются блокировкой строки. Ответ 200 на отмену
означает, что эффект этого задания больше не сможет зафиксироваться. При этом
замороженный процесс или его вычисление не обязательно физически остановлены.
Если успешное завершение произошло раньше отмены, возвращается 409, а эффект
сохраняется. При таймауте или 503 после POST повторяйте **тот же ключ и те же
данные**: результат фиксации транзакции может быть неизвестен клиенту.
Ключи идемпотентности хранятся бессрочно.

Пагинация выполняется по возрастающему ID с курсором; это не снимок состояния БД.
Порядок выделения ID не совпадает с порядком фиксации транзакций: при конкурентных
вставках можно пропустить ещё не зафиксированную запись с меньшим ID после
продвижения курсора. Для согласованной полной выгрузки остановите запись или
используйте снимок БД.

## Архитектура

API записывает задание в PostgreSQL. Триггер в той же транзакции создаёт outbox.
Отдельный `cmd/publisher` публикует ID в durable quorum queue RabbitMQ с persistent
сообщением, обязательной маршрутизацией и ожиданием подтверждения. Воркеры получают
сообщения с prefetch=1 и ручным ACK; обычного опроса jobs в их рабочем цикле нет.

PostgreSQL остаётся источником истины. Claim конкретного ID, heartbeat, отмена,
fencing и атомарность `job_effects` с итоговым статусом сохранены. Повторная доставка
не означает повторный эффект. Publisher каждые пять секунд сверяет queued и
просроченные running с outbox; повторная доставка назначается не ранее 30 секунд
после предыдущей публикации. Неверные сообщения уходят в `soup.dead`.

Один узел RabbitMQ с quorum queue не обеспечивает HA. Полный разбор отказов,
ACK и гарантий — [ARCHITECTURE_V2.md](ARCHITECTURE_V2.md).

## Метрики, трассы и Grafana

```bash
OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4318 docker compose --profile observability up -d --build
```

Grafana: http://127.0.0.1:3000, пользователь `admin`, локальный пароль
`local-grafana-change-me` (изменяется через `GRAFANA_PASSWORD`). Дашборд «Soup — очередь
задач» и источники Prometheus/Tempo подключаются автоматически. В Explore можно
выбрать Tempo и найти трассы. API и процессы экспортируют метрики на внутреннем
порту 9090. Порты PostgreSQL, RabbitMQ, Prometheus, Alertmanager, Collector и Tempo
на хост не публикуются. Управление RabbitMQ также остаётся внутри сети.

Правила находятся в `observability/alerts.yaml`: выражения и длительности `for`
можно изменить перед запуском. Значения демонстрационные: 15 секунд недоступности,
5% HTTP 5xx за две минуты, более одной повторной попытки в секунду, 1 GiB свободного
диска RabbitMQ. Их нужно согласовать с SLO, скоростью поступления и размером диска.
Уведомления направляются в локальный webhook `alert-receiver`, который пишет JSON
в Docker logs. Реальные email/Telegram не подключены. Для них нужно заменить
receiver в `observability/alertmanager.yaml`, передать секреты защищённым способом
и проверить доставку тестовым событием.

Отказ мониторинга не отменяет задания; трассы при недоступности Collector могут
теряться. Ресурсные панели показывают процессы Go/RabbitMQ, а не полный учёт ресурсов
хоста. Отдельный PostgreSQL exporter не добавлен: нужные состояния и доступность
считывает ограниченный по времени коллектор API. Это не заменяет подробный мониторинг БД.

## Конфигурация

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DATABASE_URL` | Обязательна для бинарников; Compose задаёт её сам | Строка подключения pgx |
| `API_PORT` | 8080 | Порт хоста в Compose, привязанный к loopback |
| `HTTP_ADDR` | `:8080` | Адрес HTTP-сервера; проверка готовности в Compose рассчитана на порт 8080 |
| `API_TOKEN` | Пустая при локальном запуске | Необязательный общий bearer-токен; обязателен в конфигурации VPS |
| `POSTGRES_PASSWORD` | local-development-only | Только для локальной демонстрации; VPS требует явно заданный секрет |
| `DB_MAX_CONNS` | 8 на процесс | От 1 до 64; суммарный размер пулов нужно согласовать с лимитом сервера в 150 соединений |
| `LEASE_DURATION` | 3s | Срок аренды от 300ms до 1m, определяется временем PostgreSQL |
| `HEARTBEAT_INTERVAL` | 750ms | Положительный интервал, не больше трети срока аренды |
| `POLL_INTERVAL` | 100ms | Сохранена для совместимости конфигурации V1; доставка V2 её не использует |
| `RABBITMQ_URL` | Compose формирует из `RABBITMQ_PASSWORD` | AMQP-подключение publisher и воркеров |
| `RABBITMQ_PASSWORD` | local-development-only | Пароль локального брокера; VPS требует секрет |
| `GRAFANA_PORT` | 3000 | Порт Grafana на loopback |
| `GRAFANA_PASSWORD` | local-grafana-change-me | Начальный пароль администратора Grafana |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Пустая | Для профиля наблюдаемости: `http://collector:4318` |
| `TEST_CLOCK_OFFSET` | 0s | Тестовое смещение диагностического времени процесса; не влияет на решение о действительности аренды |

Таймаут SQL-оператора — 4s, ожидания блокировки — 2s, бездействия в транзакции — 5s;
контекст операции ограничен 5s. HTTP-таймауты: заголовки — 3s, чтение — 6s,
запись — 10s, простой соединения — 30s. Одновременно работают не более 64
HTTP-обработчиков; лишние запросы получают 503 и заголовок `Retry-After`.

При SIGTERM сервер даёт HTTP-запросам до 8s на завершение, а воркеры прекращают
работу. Прерванные задания восстанавливаются после истечения аренды. Даже штатная
остановка воркера может израсходовать попытку. Если воркер не смог запуститься,
он завершает процесс, а Compose перезапускает его.

## Воспроизведение проверок

```bash
go build ./...
go test -v ./...              # Тесты БД явно пропускаются без настройки одноразовой БД
go test -race ./...
go vet ./...
go run golang.org/x/vuln/cmd/govulncheck@v1.9.0 ./...
docker compose build
python3 tests/smoke.py        # Четыре реплики по умолчанию и изоляция портов
python3 tests/integration.py  # Go-тесты с настоящей БД, пауза/возобновление, отказ БД
python3 tests/v2.py           # Отказы брокера, метрики, уведомление и сквозная трасса
python3 tests/race.py         # Go race detector с изолированной PostgreSQL
python3 tests/chaos.py --jobs 10000 --workers 8 --seed 42
python3 tests/chaos.py --jobs 10000 --workers 8 --seed 42
python3 tests/load.py --rps 100 --duration 60
python3 tests/load.py --rps 100 --duration 60
```

Python-тесты используют только стандартную библиотеку. Каждый запуск создаёт
отдельный Compose-проект `soup-test-*` со случайным именем, собственными учётными
данными и портом API на loopback. Перед отправкой сигнала контейнеру проверяются
метки проекта и сервиса. В блоке `finally` удаляются контейнеры, сеть и том
именно этого тестового проекта.

Тест с race detector дополнительно публикует одноразовую БД на случайном порту,
доступном **только через loopback**, чтобы локальные Go-тесты могли подключиться
к ней. Существующие приложения и посторонние контейнеры не останавливаются.
Доступ к Docker socket нужен только тестам; API и воркерам он не предоставляется.

Каждый запуск создаёт каталог внутри `results/v2/` с временной меткой в имени.
В нём сохраняются сводка, исходный вывод Docker, записи HTTP-запросов, логи
контейнеров и итоговый снимок БД. `tests/run.py LABEL command...` дополнительно
сохраняет неизменённый объединённый stdout/stderr и код завершения команды.
Неуспешные запуски также сохраняются. Пример:
`python3 tests/run.py chaos python3 tests/chaos.py`.

Если сам тестовый процесс завершён через SIGKILL, блок `finally` не выполнится.
Найдите точное имя проекта в `run.log` и проверьте `docker compose ls`, прежде чем
вручную удалять этот тестовый проект. Не используйте глобальную очистку контейнеров.

Фиксированный seed воспроизводит данные и план операций, но не планирование ОС,
случайные ID контейнеров, сетевые задержки или точный выбор аварийно завершаемого
процесса. Фактические действия записаны в журнале событий. Chaos-тест дополнительно
отправляет повторы в количестве 50% от числа заданий и попытки отмены в количестве
20%; длительность работы равномерно выбирается от 20 до 60ms. Реальное ML-обучение
требует другого профиля нагрузки. Короткая аренда намеренно делает тест чувствительным
к задержкам и остановкам процессов.

Нагрузочный тест отправляет уникальные POST по временному расписанию независимо
от скорости ответов — это модель open loop. Автоматических повторов HTTP-запросов
нет. Измеряются HTTP-задержки, отставание генератора запросов, фактическая частота,
ошибки и остаток очереди после нагрузки и после завершения обработки.
**100 запросов к API в секунду не означают 100 завершённых заданий в секунду.**
При сравнении производительности не запускайте нагрузочный и chaos-тест одновременно.

## Ubuntu VPS: дополнительный вариант развёртывания

Этот вариант не запускался на реальном VPS.

Установите Docker Engine и Compose по официальной инструкции Docker для Ubuntu.
Используйте отдельный каталог развёртывания и закрытый файл переменных окружения.
Конфигурация не задаёт фиксированные имена контейнеров, внешние сети или глобальные
тома. Сгенерируйте секреты в шестнадцатеричном формате, чтобы пароль не требовал
экранирования в URL подключения:

```bash
umask 077
printf 'POSTGRES_PASSWORD=%s\nAPI_TOKEN=%s\nRABBITMQ_PASSWORD=%s\nGRAFANA_PASSWORD=%s\nAPI_PORT=18080\n' \
  "$(openssl rand -hex 32)" "$(openssl rand -hex 32)" \
  "$(openssl rand -hex 32)" "$(openssl rand -hex 32)" > .env.vps
docker compose --env-file .env.vps -p soup-vps -f compose.yaml -f compose.vps.yaml up -d --build
docker compose --env-file .env.vps -p soup-vps -f compose.yaml -f compose.vps.yaml ps
curl http://127.0.0.1:18080/health
docker compose --env-file .env.vps -p soup-vps -f compose.yaml -f compose.vps.yaml down
```

API остаётся доступным только на `127.0.0.1`, а PostgreSQL не публикует порт
на хосте. Для удалённого доступа используйте SSH-туннель либо отдельно настроенный
обратный прокси с TLS и контролем доступа.

Изменение пароля в `.env.vps` не меняет пароль роли в уже существующей БД:
ротацию нужно выполнить согласованно с изменением роли PostgreSQL. Перед обновлением
создайте резервную копию средствами, учитывающими работу PostgreSQL.
Не выполняйте `down --volumes` для проекта с ценными данными. Агент не подключался
к реальному VPS.

## Известные ограничения

Используется одна БД; резервное восстановление, высокая доступность и переключение
при отказе не проверены. Есть общий bearer-токен, но нет пользователей,
разграничения доступа между клиентами, TLS-терминации, квот или распределённого
ограничения частоты запросов. Размер очереди не ограничен; ключи идемпотентности
и эффекты хранятся бессрочно.

Приложение использует роль, созданную при первоначальной настройке БД; её права
избыточны для production. Нет проверенных эксплуатационных регламентов, постоянного
журнала каждой попытки, политики удаления и архивирования данных, гарантии
справедливого порядка обработки или протокола для внешних побочных эффектов.

Теги образов могут обновляться. Сохранённые ID указывают, какие сборки проверялись,
но фиксация образов по digest и сканирование цепочки поставки остаются задачами
развёртывания. Миграция схемы версии 1 допускает повторный запуск при первоначальном
развёртывании, но не заменяет полноценный механизм обновления схемы.

Скачки часов БД могут привести к преждевременному или запоздалому истечению аренды.
После повторного получения задачи fencing по-прежнему отклоняет запись прежнего
владельца, однако своевременность обработки может пострадать. Потеря хранилища
PostgreSQL или восстановление старой резервной копии могут привести к потере
принятых заданий и эффектов.

Конечный chaos-тест не доказывает корректность при всех возможных порядках
конкурентных операций, сетевых разделениях, заполнении диска, многочасовых паузах,
перезагрузке хоста или длительном росте таблиц и индексов с работой vacuum.
Границы выполненных проверок описаны в отчёте.

## Сборка зависимостей

Зависимости закреплены в go.mod/go.sum и включены в `vendor/`. Docker собирает
приложение с `-mod=vendor`: скачивание модулей во время сборки не требуется.
После осознанного обновления зависимостей выполните `go mod tidy` и `go mod vendor`,
затем повторите тесты и сканирование. Исходные неудачные попытки сетевой сборки
сохранены в `results/v2/`.
