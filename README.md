# Soup — очередь задач (V2)

Небольшой сервис на Go, который принимает задания по HTTP, ставит их в очередь и передаёт воркерам. Основной акцент здесь на отказоустойчивости: задача не должна пропасть при падении воркера, а один и тот же результат не должен записываться дважды.

Проект использует PostgreSQL, RabbitMQ и восемь воркеров для проверки по ТЗ. Для наблюдения за работой есть Prometheus, Grafana, Alertmanager и OpenTelemetry с Tempo.

## 🚀 Быстрый запуск

Понадобятся **Docker Desktop / Docker Engine** с **Docker Compose v2.24.4+** и свободные порты **8080** и **3000**. Для Python-тестов нужен **Python 3.10+**. Устанавливать Go локально не требуется: приложение собирается в Docker.

Откройте терминал в корне проекта, где находится `compose.yaml`.

**Запуск сервиса без Grafana:**

```bash
docker compose up -d --build
docker compose ps
curl -f http://127.0.0.1:8080/health
```

При таком запуске поднимаются API, PostgreSQL, RabbitMQ, publisher и **четыре воркера по умолчанию**.

**Запуск вместе с мониторингом (рекомендуемый вариант):**

```bash
OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4318 \
  docker compose --profile observability up -d --build

docker compose --profile observability ps
curl -f http://127.0.0.1:8080/health
```

После запуска доступны:

| Что открыть | Адрес |
|---|---|
| API | http://127.0.0.1:8080 |
| Проверка API | http://127.0.0.1:8080/health |
| Grafana | http://127.0.0.1:3000 |

Для локальной Grafana стандартный логин — `admin`, пароль — `local-grafana-change-me` (если не переопределён через `GRAFANA_PASSWORD`). Дашборд **«Soup — очередь задач»** подключается автоматически.

Чтобы получить **8 воркеров**, как в задании:

```bash
docker compose up -d --no-build --scale worker=8 worker
docker compose ps worker
```

В Grafana на панели **«Потребители»** должно отображаться 8 подключений, если каждый воркер подключился к очереди RabbitMQ.

> **Авторизация:** в стандартной локальной конфигурации `API_TOKEN` пустой и API доступен без Bearer-токена только через опубликованный адрес `127.0.0.1`. Это режим для разработки, а не настройка для публичного сервера. Чтобы включить токен, задайте `API_TOKEN` в `.env` перед запуском. Образец конфигурации — `.env.example`.

## 🧪 Проверка API вручную

Создадим задание:

```bash
curl -i -X POST http://127.0.0.1:8080/jobs \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: readme-example-001' \
  -d '{"model":"demo","duration_ms":1000,"max_attempts":5}'
```

В ответ придёт JSON с идентификатором и состоянием задания. Скопируйте полученный `id` и подставьте вместо `123` в следующие команды:

```bash
# Посмотреть конкретное задание
curl http://127.0.0.1:8080/jobs/123

# Получить страницу списка заданий
curl 'http://127.0.0.1:8080/jobs?limit=20&after=0'

# Попробовать отменить задание
curl -X POST http://127.0.0.1:8080/jobs/123/cancel
```

Если повторить первый POST **с тем же ключом и теми же данными**, вернётся то же задание, а не новое. Если использовать тот же ключ, но изменить данные, API ответит `409 Conflict`.

Если задача уже закончила работу, запрос отмены тоже может вернуть `409` — это нормальная ситуация. При включённом `API_TOKEN` к запросам, кроме `/health`, нужно добавлять `-H "Authorization: Bearer $API_TOKEN"`.

Основные маршруты:

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/jobs` | Создать задачу с `Idempotency-Key` |
| GET | `/jobs/{id}` | Получить состояние одной задачи |
| GET | `/jobs?limit=20&after=0` | Получить список с пагинацией |
| POST | `/jobs/{id}/cancel` | Отменить задачу, если ещё возможно |
| GET | `/health` | Проверить доступность API и PostgreSQL |

Состояния задания: `queued`, `running`, `succeeded`, `failed`, `cancelled`.

## 🏗️ Как устроена система

Клиент отправляет POST-запрос в Go API. API записывает задачу в PostgreSQL, а в той же транзакции создаётся запись в `outbox`. Отдельный publisher отправляет сообщение в RabbitMQ. Воркер получает его, захватывает задачу через PostgreSQL, выполняет работу и сохраняет результат.

PostgreSQL остаётся источником истины о состоянии задания. RabbitMQ отвечает за доставку сообщений, но может доставить сообщение повторно. Поэтому используется **at-least-once** для попыток обработки и защита от повторного побочного эффекта в PostgreSQL.

Если воркер упал, его аренда (`lease`) перестаёт продлеваться. После истечения аренды задачу сможет забрать другой воркер. Проверка токена владения (`fencing token`) не позволяет старому воркеру записать результат после того, как задачу перехватили.

Подробности приведены в [ARCHITECTURE_V2.md](ARCHITECTURE_V2.md).

## 💥 Как запускать тесты

Есть **два режима**. Не путайте их:

- **Изолированный** — тест создаёт собственный временный Compose-проект с отдельной БД. Это вариант для проверки корректности, не затрагивающий основное окружение. Основная Grafana его не показывает.
- **На работающем сервисе (`--base-url`)** — тест обращается к API на порту 8080, поэтому результаты видны в основной Grafana. Задания сохраняются в действующей БД. Режим chaos действительно принудительно завершает её воркеры.

### 1. Безопасные изолированные тесты

Нужен запущенный Docker. Команды выполняются из корня репозитория:

```bash
python3 tests/smoke.py
python3 tests/integration.py
python3 tests/v2.py
python3 tests/race.py

# 10 000 заданий, 8 воркеров, SIGKILL примерно каждые 2 секунды
python3 tests/chaos.py --jobs 10000 --workers 8 --kill-interval 2 --seed 42

# 100 запросов/с в течение 60 секунд
python3 tests/load.py --rps 100 --duration 60
```

Эти проверки используют отдельные контейнеры и не должны выполняться одновременно с другим тяжёлым тестом. Для `race.py` также нужен локальный Go, поскольку он запускает `go test -race` на компьютере.

### 2. Нагрузочный тест, который видно в основной Grafana

Сначала запустите сервис с мониторингом. Для локального API **без токена** выполните:

```bash
python3 tests/load.py \
  --base-url http://127.0.0.1:8080 \
  --project-name soup_back \
  --allow-unauthenticated \
  --rps 100 \
  --duration 60
```

Создаются **6 000 заданий в действующей БД**. Тест ждёт завершения их обработки и сверяет записи в PostgreSQL. Если API защищён, не используйте `--allow-unauthenticated`: передайте настоящий токен через переменную окружения `API_TOKEN`.

### 3. Chaos-тест по ТЗ, который видно в Grafana

**Внимание:** этот режим отправляет `SIGKILL` воркерам основного проекта и создаёт **10 000 настоящих записей**. Используйте его только в локальном тестовом окружении, где нет ценных заданий.

Сначала убедитесь, что работающих воркеров ровно восемь и что старые задачи завершились:

```bash
docker compose up -d --no-build --scale worker=8 worker
docker compose ps worker
```

Затем запустите:

```bash
python3 tests/chaos.py \
  --base-url http://127.0.0.1:8080 \
  --project-name soup_back \
  --allow-unauthenticated \
  --allow-worker-kills \
  --jobs 10000 \
  --workers 8 \
  --kill-interval 2 \
  --timeout 300
```

Тест создаёт 10 000 уникальных заданий, параллельно проверяет 5 000 повторных POST с теми же ключами и отправляет 2 000 запросов отмены. Примерно раз в две секунды один из восьми воркеров завершается через `SIGKILL`, после чего перезапускается.

После нагрузки проверяются конечные состояния, число записей побочных эффектов, отсутствие потерянных заданий и зависших `queued`/`running`. Тест откажется запускать внешний chaos, если в БД уже есть незавершённые задания. Разрешение `--allow-worker-kills` обязательно.

**Если Compose-проект называется не `soup_back`,** посмотрите его имя через `docker compose ls` и замените значение `--project-name` в командах.

### 4. Где результаты

Результаты находятся в `results/v2/`. Каждый запуск создаёт отдельный каталог с датой и временем. Для внешнего chaos-теста там могут быть:

- `summary.json` — итоговые числа и `passed`;
- `run.log` — события запуска;
- `requests.ndjson` — записи HTTP-запросов;
- `kill-events.json` — завершения и перезапуски воркеров;
- `final-db.json` — результаты проверки записей БД.

Сохраняйте эти файлы при передаче тестового задания: они позволяют воспроизвести и проверить выводы, а не просто доверять сводке.

## ⚠️ Ограничения и вердикт

**Вердикт: DON'T SHIP** для реального продакшна в текущем виде. Тесты показывают, что система работает в проверенных сценариях, но для промышленного развёртывания пока не хватает отказоустойчивой PostgreSQL, проверенного восстановления из резервных копий, ограничений роста очереди и длительных нагрузочных тестов. Также необходимо включить аутентификацию и настроить безопасный внешний доступ.

Имитируемый побочный эффект сохраняется в PostgreSQL. Гарантию отсутствия повторного *внешнего* действия (например, платежа или отправки сообщения в стороннюю систему) этот проект пока не предоставляет.

```bash
# Посмотреть состояние контейнеров
docker compose ps

# Посмотреть логи
docker compose logs -f --tail=100 api publisher worker

# Вернуться к четырём воркерам
docker compose up -d --no-build --scale worker=4 worker

# Остановить сервисы, сохранив данные

# ОСТОРОЖНО: удалит также тома с данными проекта
# docker compose --profile observability down --volumes
```
