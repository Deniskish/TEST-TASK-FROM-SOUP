# Отчёт V2: RabbitMQ и наблюдаемость

**DON'T SHIP.** Основные проверки доставки и прежних инвариантов прошли, но один
узел RabbitMQ и одна PostgreSQL не обеспечивают HA. Не проверены потеря диска,
восстановление из резервной копии, многосуточная нагрузка и сетевые разделения.
Нет разграничения доступа по владельцам задач и ограничения общего размера очереди.

## Изменения и гарантии

RabbitMQ доставляет ID задач, PostgreSQL хранит состояния, ключи, аренду и эффекты.
Миграция 002 создаёт outbox и триггер: запись задания без события не фиксируется.
Проверка `TestOutboxAtomicity` намеренно ломает вставку outbox и проверяет откат jobs.
Publisher использует persistent, mandatory и confirms. ACK воркера следует после
фиксации результата либо чтения терминального состояния. Сохранены fencing,
проверка времени после блокировки и единая транзакция для эффекта и succeeded.

Включаемый профиль содержит Prometheus, Grafana, Alertmanager, Collector и Tempo.
Контекст трассы проходит через PostgreSQL/outbox и заголовки AMQP. Проверен один
trace с `postgres.Create`, `outbox.publish`, `worker.process`, `postgres.Finish`.
Метрики и dashboard проверены через API работающих сервисов, а не только по файлам.

## Реальные проверки

[Все запуски и коды завершения V2](results/v2/INDEX.md) хранятся отдельно от V1.
Выполнены сборка, unit/race/vet, race с настоящей БД, регрессионная интеграция,
три chaos-прогона по 10 000 задач и четыре нагрузки по 6000 запросов за 60 секунд.
Нарушений инвариантов в успешных прогонах не обнаружено. Итоговый chaos: 8171
succeeded, 1829 cancelled, 0 failed/running/queued; 26 SIGKILL, 19 задач с повторным
получением. Это конечные наблюдения, не доказательство всех возможных порядков событий.

`tests/v2.py` проверяет дубликаты и неверные сообщения в DLQ, остановку RabbitMQ
при публикации, сохранение outbox при недоступном брокере, перезапуск во время
выполнения, недоступность PostgreSQL после доставки и отказ API принимать запись
без БД. Отдельно воркер убивается после succeeded, но до ACK: повторная доставка
не увеличивает attempts и не создаёт второй эффект. Прежний integration проверяет
pause/resume zombie, Cancel/Finish, исчерпание попыток, откат эффекта и перегрузку.

Последний прогон V2 также проверил возобновление публикации после простоя и
восстановление после SIGKILL publisher. Проверка стандартного Compose с четырьмя
воркерами прошла.

Все девять правил Alertmanager/Prometheus прошли `promtool test rules` с явными
входными временными рядами: проверены срабатывания, отсутствие срабатывания
на здоровых рядах и ожидание `for` для PostgreSQL. Реальный переход в firing и webhook-доставка проверены
для RabbitMQUnavailable. Остальные правила не проверялись всеми физическими
отказами инфраструктуры. Email/Telegram не настроены: receiver только пишет JSON
в Docker logs. Временные ряды правил — тестовые входные данные, а не метрики нагрузки.

## Нагрузка и ресурсы

Сравнение итоговой сборки, восемь воркеров, задачи по 40ms, одна локальная машина:

| Профиль | Факт RPS | p50 / p95 / p99, ms | Успех / ошибка | Остаток после обработки |
|---|---:|---:|---:|---:|
| Без наблюдаемости | 99.999 | 1.952 / 2.705 / 4.297 | 6000 / 0 | 0 |
| С наблюдаемостью и экспортом трасс | 99.998 | 1.972 / 2.821 / 4.756 | 6000 / 0 | 0 |

Сумма памяти контейнеров по `docker stats` после нагрузки: 264.061 MiB без профиля
и 558.618 MiB с ним. При старте: 232.790 и 414.035 MiB. Это моментальные снимки,
**не максимум RSS и не полная память Docker VM**. Окружение — macOS/arm64,
Docker Linux aarch64, VM 8 CPU и около 7.75 GiB RAM. Точные версии образов и снимки
ресурсов есть в summaries. На слабом VPS профиль разумно включать отдельно.

Два ранних замера дали p99 21.337 и 39.973ms: они пересекались с подготовкой
образов/другими проверками на общей машине и не используются для вывода о накладных
расходах. Все исходные измерения сохранены. Даже чистая пара — по одному короткому
прогону; статистически надёжное сравнение по ней невозможно.

Исторический V1 на той же машине завершал chaos примерно за 48 секунд, итоговый
V2 — за 62.81 секунды. Это наблюдаемое ухудшение времени конкретного сценария,
а не строго изолированная оценка цены RabbitMQ. Новая архитектура добавила broker,
publisher, outbox-записи и дополнительные точки отказа. Преимущество здесь —
доставка без постоянного опроса jobs воркерами, а не доказанный рост производительности.

## Найденные проблемы и исправления

- Ошибка publisher сохраняла `ErrNoRows` на следующую итерацию. Периодическая
  сверка сбрасывала её каждые пять секунд, поэтому появлялись паузы публикации.
  Ошибка исправлена сбросом результата перед итерацией; отдельный тест проверяет
  новую публикацию после простоя. Это найдено просмотром кода, не провалом chaos.
- Первый тест наблюдаемости завершился с Connection refused к Management API.
  Повтор подтвердил смену случайного порта Docker после рестарта: 64693 → 52127.
  Harness теперь заново читает порт. Неуспешный запуск сохранён.
- Правило ProcessingStalled сопоставляло разные метки state и не могло сработать.
  Добавлено `ignoring(state)`, затем проверены все девять правил.
- `govulncheck` обнаружил пять достижимых известных уязвимостей в x/net 0.59.0.
  Обновление до 0.60.0 убрало достижимые findings. Сканер также указал две
  уязвимости в требуемых модулях без обнаруженного вызова уязвимого кода; это не
  безусловное утверждение об отсутствии риска.
- Две Docker-сборки оборвались с EOF при загрузке разных модулей. Причина сетевого
  обрыва не установлена. Добавлен vendor из проверенных модулей; следующая сборка
  прошла без скачивания зависимостей. Старые неуспешные логи сохранены.

- Итоговая проверка race с БД сначала упала на завершающем Python-валидаторе:
  новый Go-тест outbox оставлял созданную задачу в queued на стенде без воркеров.
  Сам Go race detector ошибок не сообщил. Тест теперь явно отменяет эту задачу;
  неуспешный запуск сохранён для проверки причины. Повторный прогон с настоящей
  PostgreSQL прошёл; отдельный `go test -race ./...` также завершился успешно.

## Что происходит при отказах

| Компонент | Поведение |
|---|---|
| PostgreSQL | API возвращает ошибку вместо принятия задачи. Воркер не фиксирует эффект и не подтверждает незавершённую работу; после восстановления возможен повтор. |
| RabbitMQ | Новые задачи остаются в PostgreSQL/outbox. Доставка останавливается, publisher переподключается. Сохранённые сообщения восстанавливаются с тома, сверка страхует пропущенную доставку. |
| Publisher | Неподтверждённая публикация остаётся в outbox. Смерть после confirm до COMMIT допускает дубликат. |
| Worker | Брокер повторяет неподтверждённую доставку; lease/fencing решают право выполнения. После COMMIT до ACK терминальное состояние предотвращает повторный эффект. |
| Collector/Tempo | Экспорт может потерять трассы; задания продолжают выполняться. |
| Prometheus/Grafana | Наблюдение недоступно, очередь продолжает работать. |
| Alertmanager/receiver | Уведомления не гарантированы; бизнес-транзакции от них не зависят. |

Reconciliation имеет задержку до периода сверки плюс 30-секундный порог повторной
публикации. Восстановление через неё медленнее прежнего прямого опроса просроченных
jobs. Если воркеры долго отсутствуют, повторные публикации могут увеличивать очередь;
DLQ и outbox требуют политики хранения. Эти ограничения не скрыты за словом HA.

## Перед production

Нужны отдельные роли БД, политика хранения/DLQ и ограничения очереди, контроль
доступа к заданиям, секреты и TLS, backup/restore с проверенным RPO/RTO, настройка
SLO и длительные испытания. Пороги alerts демонстрационные и меняются в YAML.
Один quorum-узел нельзя считать кластером. На VPS агент не подключался.

# Отчёт: Soup Internship — Backend Engineer

**Вердикт: DON'T SHIP для промышленного использования при 100 RPS.** Локально сервис выдержал
заданный поток запросов и проверенные отказы, но эксплуатационные требования и требования безопасности
реального production не закрыты. Это не обнаруженная потеря задач: это предел
обоснованности положительного решения на данных тестах.

## Что реализовано

Исходный PDF прочитан до разработки; [извлечение](results/original-requirements.txt)
сохранено. `design.md` создан до Go-кода. Структура находится прямо в корне текущего
репозитория, без лишнего вложенного `soup-job-queue/`.

REST endpoints создания, просмотра, keyset списка, отмены и health; PostgreSQL
queue; четыре default worker-процесса и масштабирование до восьми; persisted
idempotency; READ COMMITTED, row locks/SKIP LOCKED, DB-clock lease/heartbeat,
fencing; атомарный effect + succeeded; retries и исчерпание попыток; таймауты,
ограниченные pools и HTTP handlers; graceful shutdown. Реального ML нет.

Есть независимые Python chaos/load/integration harness, SQL assertions, Go unit и
DB tests, реальная freeze/resume проверка, проверка валидатора на намеренно испорченных данных валидатора и краткий
тест перегрузки. Docker Compose и VPS overlay; README/API contract,
security review, AI disclosure и русскоязычный walkthrough.

Во всех приведённых успешных прогонах: `queued=running=0`; `job_effects` ровно
столько, сколько succeeded; ни одного эффекта у failed/cancelled; effect token
совпадает с текущим token; карта принятых key→id точно совпала с БД; дубликатов keys
и эффектов не обнаружено. Каждая задача с attempts>1 в этих прогонах была получена
повторно: simulated failures здесь выключены. Отменилось меньше 2 000, поскольку
часть cancel проиграла уже завершившимся задачам (409 — ожидаемый контракт).

Это подтверждает восстановление наблюдавшихся crash-сценариев и отсутствие
перечисленных нарушений в конце этих запусков. Это не доказательство exactly-once
execution, бесконечного прогресса при произвольных отказах или отсутствия всех
возможных interleavings. Сами обработчики могли стартовать повторно; уникален
зафиксированный DB effect.

## Нагрузка: 100 HTTP RPS

Каждый прогон: 60s, 6 000 уникальных POST, 64 client threads, 8 workers,
имитация задачи 40ms. Open-loop scheduling, без автоматических HTTP retries.
Первые две серии измерений сохранены отдельно от окончательной C.

## Проверки сборки, ошибки и исправления

Go build, модульные тесты, vet, race detector выполнены; DB tests в обычном локальном
запуске явно SKIP без TEST_DATABASE_URL, затем реально выполнены в disposable DB,
включая host `go test -race` с опубликованным только на loopback временным DB port.
Сборка Docker выполнена. Smoke тест запускает Compose **без --scale**, проверяет
четыре worker-контейнера, приватные ports и успешную задачу. VPS overlay проверен
`docker compose config --quiet`; на реальном VPS ничего не запускалось.

Реальный отрицательный результат: первый `govulncheck` сообщил о четырёх уязвимостях
и завершился ненулевым кодом. Исходный лог
[сохранён](results/20261111T091255Z-govulncheck-769f31.log). Подробности applicability
и источники в [SECURITY_REVIEW.md](SECURITY_REVIEW.md). Это сообщение сканера, не
доказательство успешно проведённой атаки на сервис. После обновлений повторный
[scan](results/20261111T091655Z-patched-vuln-210ee0.log) сообщил
`No vulnerabilities found.` Затем повторены runtime suites.
[Повторный scan окончательного кода C](results/20261111T092915Z-release-vuln-69ab30.log)
также не обнаружил известных уязвимостей.

На финальном просмотр кода rollback получил отдельный deadline 2s. Это устраняет
неограниченный cleanup context по коду; silent packet blackhole отдельно не
воспроизводился. Поэтому не утверждается, что проверены все варианты сетевого
отказа. PostgreSQL stop/connection termination проверены фактически.

Сначала Docker daemon не работал; после запуска Docker Desktop полноценные тесты
стали доступны. Для чтения PDF отсутствовал pymupdf, использован pypdf в локальном
venv. Это ограничения начальной среды, а не причины ошибок очереди. Все запущенные
тестовые команды и сканер outcomes доступны в индексе, неуспешные не удалялись.

## Что оказалось неожиданным и что беспокоит

Успешные concurrent, crash и нагрузочные тесты сосуществовали с известными
уязвимостями первоначально выбранных зависимостей. Это конкретный результат
проверок, а не аргумент считать зелёные тесты бесполезными: они проверяли другие
свойства. Ещё одно заметное наблюдение — при одинаковом seed различаются исходы
отмен и число reclaimed jobs: seed не контролирует ОС и PostgreSQL scheduler.
Больше всего беспокоит неограниченная очередь на долгих задачах и центральная зависимость
от сохранности одной PostgreSQL, которые быстрый имитатор не способен обосновать.

## Почему DON'T SHIP и что сделать первым

1. **Ограничить admission и доступ.** Tenant/job ownership или явно ограниченный
   trusted-internal сценарий, quotas, backlog/disk limits, TLS/reverse proxy;
   заменить первоначальную роль суперпользователя на отдельные app/migration роли. Общий bearer
   token реален, но даёт доступ ко всем jobs.
2. **Обеспечить сохранность и эксплуатацию.** Проверенный резервное копирование и восстановление и RPO/RTO,
   мониторинг возраста очереди, latency/errors, lease recovery и disk; alerting,
   retention и процедуры upgrade. HA/failover — по требуемой доступности, не ради
   увеличения количества технологий.
3. **Проверить целевую нагрузку.** Длительный soak с длинными задачами, ростом таблиц,
   реальным proxy/TLS, ресурсными лимитами, disk-full и сетевыми partition. Уточнить
   SLO и только после этого принимать решение о готовности к эксплуатации.

Не выполнены и не заявляются: deployment на Ubuntu VPS, многосуточная нагрузка,
реальное изменение системных часов/DB clock jumps, disk-full, восстановление из резервной копии,
HA failover, все варианты COMMIT response loss, packet blackhole и полноценный
тест на проникновение и сканирование образов контейнеров. Основные исполняемые требования
задания реализованы и локально проверены; clock-skew проверка ограничена явно
описанной моделью. Неразрешённой наблюдавшейся ошибки lifecycle в успешных прогонах
не осталось, но отсутствие обнаруженной ошибки не доказывает её невозможность.

Проверки запускал агент. Для независимой оценки следует воспроизвести команды
README и проверить получение задач, идемпотентность и взаимодействие завершения
с отменой. Репозиторий и письмо с решением никуда не отправлялись.
