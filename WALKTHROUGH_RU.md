# Путь задания в V2

1. HTTP-обработчик нормализует данные и вызывает `Store.Create`. Триггер
   `enqueue_job` записывает outbox в той же транзакции, что и jobs.
2. `cmd/publisher` выбирает одну строку outbox под блокировкой. Контекст трассы
   восстанавливается из JSON, публикация получает отдельный span. Persistent
   сообщение содержит только ID и W3C-заголовки трассы.
3. После confirm без basic.return publisher помечает событие опубликованным.
   Авария между confirm и COMMIT допускает дубликат. Это ожидаемый случай.
4. `internal/worker` получает доставку с prefetch=1. `ClaimID` использует прежние
   транзакции и fencing, но выбирает ID сообщения вместо очередного ID из очереди.
5. После успешного `Finish` отправляется ACK. Терминальное задание подтверждается
   без вычисления. Неверное или уже занятое сообщение отклоняется в DLQ;
   reconciliation обеспечивает будущую доставку незавершённого задания.
6. Отказ БД не допускает ACK за незавершённую работу. Канал закрывается, сообщение
   может быть доставлено снова. Действительность результата решает PostgreSQL.

`internal/telemetry` содержит гистограммы, счётчики, коллектор состояний и экспорт
OTLP. Трассировка не записывает payload, пароль или bearer-токен. Полный путь:
HTTP → postgres.Create → outbox.publish → worker.process → postgres.Finish.
Heartbeat/Cancel также имеют spans. Во время выключенного профиля экспорт OTLP
следует отключить, оставив `OTEL_EXPORTER_OTLP_ENDPOINT` пустой.

Ниже сохранён разбор механизмов PostgreSQL. В V2 `Claim` без ID оставлен для
регрессионных тестов; рабочий путь использует `ClaimID` по доставке RabbitMQ.

# Как устроен сервис

Этот документ объясняет основные пути выполнения и границы гарантий.
Краткое описание решений находится в [design.md](design.md), результаты проверок —
в [REPORT_RU.md](REPORT_RU.md).

## Точки входа и остановка

`cmd/api/main.go` запускает HTTP-сервер, `cmd/worker/main.go` — воркер.
Docker собирает два бинарника. Каждая реплика воркера работает в отдельном процессе
с собственной памятью. Поэтому очередь координируется через PostgreSQL.

Конфигурация читается из переменных окружения через `internal/config`.
`signal.NotifyContext` связывает SIGTERM/SIGINT с отменой контекста. Контекст
передаёт сигнал отмены и дедлайн вызываемому коду; сам по себе он не останавливает
произвольную функцию. pgx и HTTP используют контекст для прекращения операций.

`defer pool.Close()` освобождает пул при выходе из функции. При SIGKILL,
аварии машины или `os.Exit` отложенные вызовы не гарантированы.

## Обработка HTTP-запроса

В `internal/api/api.go` маршрутизатор `http.ServeMux` выбирает обработчик по методу
и пути. Обёртка проверяет bearer-токен, ограничивает число активных обработчиков
каналом ёмкости 64 и задаёт контекст на пять секунд. Этот канал служит семафором;
сами задания хранятся в БД.

`create` ограничивает тело 4096 байтами, отклоняет неизвестные JSON-поля и второе
JSON-значение после тела, проверяет диапазоны. `Normalize` задаёт значения по
умолчанию и удаляет пробелы по краям имени модели. Отсутствующее `max_attempts`
и явное значение 5 после нормализации эквивалентны.

Ответ 201 означает создание, 200 — повтор того же запроса, 409 — другие данные
с уже занятым ключом. При сетевой ошибке INSERT мог успеть зафиксироваться.
Поэтому повторять нужно тот же ключ: новый ключ означает новую операцию.

## Доступ к PostgreSQL и идемпотентность

`internal/storage/store.go` содержит SQL. `pgxpool` ограничивает число соединений.
`QueryRow` читает одну строку через `Scan`, `Query` возвращает набор строк;
`rows.Close` освобождает ресурсы. Параметры `$1`, `$2` отделяют значения от SQL.

В `Create` гонку двух INSERT разрешает уникальный индекс `idempotency_key`.
Предварительный SELECT без такого ограничения был бы недостаточен: оба процесса
могли бы одновременно не найти запись. Здесь один INSERT создаёт строку, второй
ждёт разрешения конфликта и читает существующее задание.

При READ COMMITTED конфликтующий `INSERT ON CONFLICT DO NOTHING` может ждать
транзакцию, строка которой не видна его исходному снимку. Поэтому чтение выполняется
следующим SQL-оператором: он получает свежий снимок. Объединение INSERT и SELECT
в один CTE потребовало бы отдельного разбора этого случая.

## Получение задачи и восстановление

`Claim` открывает короткую транзакцию. Сначала ограниченная порция просроченных
заданий с исчерпанными попытками переводится в failed. Затем SELECT выбирает
доступную задачу и блокирует строку. `SKIP LOCKED` позволяет другим воркерам
пропускать занятые строки; строгий FIFO не гарантируется.

Под блокировкой увеличиваются attempts и token, назначается аренда. После COMMIT
начинается имитация работы. Во время вычисления транзакция уже закрыта: зависший
воркер не держит соединение и не блокирует отмену или восстановление.

Отложенный вызов `rollback` страхует ранние выходы из функции. После успешного
COMMIT он безвреден. На очистку выделено две секунды, чтобы она не ждала бесконечно
при проблеме с соединением. Атомарность записи обеспечивает PostgreSQL.

## Аренда и защита от старого владельца

Аренда, или lease, задаёт срок владения задачей. Heartbeat продлевает его.
Истечение не доказывает смерть процесса: тот мог потерять сеть, быть заморожен
или долго не получать процессорное время. После восстановления два процесса
могут одновременно выполнять обработчик одной задачи.

Fencing token — возрастающий номер поколения владения. При каждом получении
задачи он увеличивается в БД. `Finish` допускает запись только при совпадении
номера, состоянии running и действующей аренде. Старый процесс не может записать
результат просто потому, что возобновил работу.

Heartbeat и завершение сначала блокируют строку, затем проверяют
`clock_timestamp()` новым оператором. Иначе срок мог бы истечь за время ожидания
блокировки. Это проверяет `TestReadCommittedAndLockWaitExpiry`.

Срок определяет PostgreSQL. `time.NewTimer` отвечает за длительность имитации,
а не за право записи. `TEST_CLOCK_OFFSET` меняет только диагностическое время
процесса. Эта проверка не моделирует изменение системных часов или часов БД.

## Эффект, завершение и отмена

В `Finish` изменение статуса и INSERT в `job_effects` входят в одну транзакцию.
Ошибка вставки откатывает и статус. Поэтому не фиксируется состояние succeeded
без эффекта. Уникальный `job_id` запрещает два эффекта. Гарантия относится к этой
БД, а не к записи файла или вызову внешнего сервиса.

`Cancel` блокирует ту же строку. Если отмена произошла первой, она ставит cancelled,
сбрасывает аренду и инвалидирует token; завершение будет отвергнуто. Если первым
было успешное завершение, отмена возвращает 409. Допустимы succeeded с одним
эффектом и cancelled без эффекта. Отменённый расчёт может продолжаться до следующей
проверки владения, особенно если процесс заморожен.

`fail_until_attempt` включает имитацию ошибки. Она возвращает задание в queued
или переводит его в failed на последней попытке. Авария оставляет running;
по истечении аренды другой воркер повторяет обработку либо завершает задание
как failed при исчерпании попыток. `attempts` считает зафиксированные получения
задания, а не эффекты или объём вычислений.

## Горутины и процессы

API запускает `ListenAndServe` в горутине, чтобы основная функция могла ждать
ошибки сервера или сигнала остановки. Результат передаётся через буферизированный
канал. Планировщик Go распределяет горутины между потоками операционной системы.

Один воркер обрабатывает одну задачу. Его `select` ждёт отмену контекста,
heartbeat или срабатывание таймера. Если заменить таймер длительным блокирующим
обучением, цикл придётся изменить: heartbeat должен продолжаться, а вычисление —
реагировать на отмену.

Race detector проверяет гонки памяти Go. Он не проверяет корректность транзакций
между процессами, поэтому дополнительно нужны тесты с чтением фактической БД.

## Устройство тестов

`tests/common.py` создаёт отдельный Compose-проект, сеть, том, временный порт
на loopback и собственные учётные данные. Перед сигналом контейнеру проверяются
метки проекта и сервиса. Действия ограничены контейнерами тестового проекта.

`chaos.py` по seed готовит данные и планы повторов и отмен. Параллельно создаются
задания, повторяются ключи, отправляются отмены и завершаются выбранные воркеры
через SIGKILL. После этого воркеры запускаются снова. Принятые пары ключ → ID
сверяются с полным состоянием БД.

Ожидание завершения ограничено таймаутом. Проверяются наличие принятых заданий,
уникальность ключей и эффектов, конечные состояния и соответствие token эффекта.
`attempts > 1` подтверждает повторное получение, но само по себе не доказывает
защиту от старого владельца. Для неё есть отдельная проверка замороженного процесса.

`load.py` отправляет запросы по расписанию независимо от скорости ответов.
Отставание генератора измеряется отдельно. HTTP-задержка не включает это ожидание,
а задержка от запланированного момента отправки включает. Остаток очереди измеряется
после нагрузки и после завершения всей обработки.

`integration.py` запускает тесты хранилища Go, проверяет HTTP и БД, приостанавливает
и возобновляет контейнер, перезапускает PostgreSQL. Проверка самого валидатора
намеренно создаёт несогласованное состояние в одноразовой БД и требует его отклонить.

## Границы гарантий

Сохранность принятых заданий зависит от сохранности БД. Восстановление старой копии
может потерять более новые записи. При остановке всех воркеров обработка не идёт;
аренда позволяет восстановить работу после их возвращения, но не заменяет доступную
БД и вычислительные процессы. Неограниченная очередь способна заполнить диск.

В проекте нет проверенного резервного восстановления, высокой доступности,
разграничения доступа между клиентами, мониторинга целевых показателей или
длительных испытаний. Общий токен позволяет читать и отменять любые задания.
Четыре воркера с секундными задачами не выполнят 100 задач в секунду, даже если API
принимает 100 POST в секунду. Быстрый имитатор не устраняет этого ограничения.
